## 1. 结论

0.7.0 不在插件中增加一套文件、shell、网络、MCP 或权限开关。DSH 已经拥有 workspace、permission preset、sandbox、approval、ToolRuntime 和 MCP client；这些服务必须继续作为唯一权威来源。

0.7.0 的核心是新增 **DSH-owned tool bridge**：

```text
DSH Web 中选择项目和权限模式
  ├─ Session.header.cwd：项目目录
  ├─ read-only | workspace-write | danger-full-access
  ├─ DSH sandbox / approval
  └─ 当前 Agent 的文件、shell、web、MCP 工具目录
            ↓
     dsh-agy-provider
       只把 DSH tool schemas 交给 AGY 模型做选择
            ↓
       AGY 返回结构化 tool call
            ↓
     Provider 发出 DSH tool-call chunks
            ↓
     DSH ToolRuntime 执行并应用当前项目和权限
            ↓
       tool result 进入下一轮模型请求
```

AGY 在这条主路径中只承担模型推理并消耗 AGY 额度，不直接执行文件、shell、网络或 MCP 工具。因此：

- 项目目录就是 DSH 创建 Session 时保存的 immutable `cwd`。
- 是否允许写入完全由 DSH 当前 permission preset 决定。
- shell、网络、MCP 是否存在由 DSH 当前 Agent/tool catalog 决定。
- 工具调用是否获准、是否询问用户、是否全权限执行由 DSH sandbox/approval 决定。
- Provider 不传 `--dangerously-skip-permissions`；DSH 的 `danger-full-access` 已经控制实际工具执行，无需再绕过 AGY 权限。

## 2. 已确认的 DSH 契约

基于 `@deepseek-ai/dsh@0.1.0-rc.7` 及其同版本公开包审计：

| DSH 能力 | 权威数据/服务 | 0.7.0 使用方式 |
|----------|---------------|----------------|
| 项目目录 | `Session.header.cwd`、`WorkspaceRegistry` | 使用 DSH 创建会话时的 canonical workspace；不从 prompt 或 Provider 配置猜测 |
| 权限选择 | `PermissionPresetService` | 接受 `read-only`、`workspace-write`、`danger-full-access` 的会话级选择 |
| 文件边界 | `SandboxPolicyService.resolve({ session })` | DSH 以 session cwd 作为 workspace-write 边界 |
| 用户审批 | `ApprovalService` | 工具执行经过 DSH ask/fail-closed/audit 流程 |
| 工具目录 | `GenerateOptions.tools` / `ToolRuntime` | Provider 转换 schema，实际调用仍由 DSH ToolRuntime 执行 |
| shell | DSH bash/pwsh tools + sandbox executor | 由 DSH 执行，Provider 不 spawn 用户命令 |
| 网络 | DSH web tools | 由 DSH 工具及其策略执行，Provider 不实现第二套网络栈 |
| MCP | `@deepseek-ai/dsh-mcp-client` 注册的工具 | 作为普通 DSH tool schema 进入桥接，不向 AGY 暴露 MCP 凭据 |

DSH 的 standard preset 为了 request-cache 稳定性，可以在不同权限模式下保持相同工具目录。因此 Provider 不按权限模式擅自删减 schemas；即使模型在 `read-only` 下请求写工具，最终也必须由 DSH sandbox 拒绝并产生可审计结果。

## 3. 用户可见行为

### 3.1 文件读写

用户在 DSH 中选择项目后，新 Session 的 `cwd` 指向该项目。用户再选择 DSH 权限模式：

| DSH 模式 | 文件读取 | 项目内写入 | 项目外写入 | 审批 |
|----------|----------|------------|------------|------|
| `read-only` | 允许 | 拒绝 | 拒绝 | 拒绝事实由 DSH 返回 |
| `workspace-write` | 允许 | 允许 | 默认拒绝，可由 DSH 的一次性审批流程处理 | `ask` |
| `danger-full-access` | 允许 | 允许 | 允许 | DSH 不产生 sandbox escalation |

Provider 不再要求用户在 `cordis.patch.yml` 中重复填写 `workspaceRoot` 才能使用 DSH-owned 工具。静态 `workspaceRoot` 只保留给 0.6.x `agy-owned` 兼容路径，并在 0.7.0 文档中标记为 legacy。

### 3.2 shell、网络与 MCP

权限模式只决定“能否执行”，工具目录决定“有没有该能力”：

- shell：DSH 当前 Agent 暴露 bash/pwsh tool 时，AGY 模型可返回该 tool call；命令由 DSH sandbox executor 执行。
- 网络：DSH 当前 Agent 暴露 web/search/fetch tool 时，模型可调用；网络限制、返回内容和审计由 DSH 管理。
- MCP：用户在 DSH 中配置并启用 MCP server 后，其 `mcp__<server>__<tool>` schema 可被模型调用；连接、凭据和执行全部留在 DSH。
- 若某能力未出现在本轮 `GenerateOptions.tools`，Provider 不把它写进模型 schema，模型也不能通过桥接调用它。

### 3.3 自动跳过权限

“自动跳过权限”只对应 DSH 已选择的 `danger-full-access`，不新增 Provider 开关：

- DSH-owned 模式下，AGY 没有内部工具，Provider 永不传 `--dangerously-skip-permissions`。
- 工具实际在 DSH 中执行，所以 DSH 的 full-access 决定已足够。
- prompt、模型输出、环境变量或 AGY event 都不能把 DSH 会话从 read-only/workspace-write 提升到 full access。
- `agy-owned` legacy 路径不宣称受 DSH 权限完整控制；0.7.0 默认迁移到 `dsh-owned`。

## 4. 关键产品决策

### 4.1 新增 `toolPolicy: dsh-owned`

- `dsh-owned` 成为 0.7.0 DSH bundle 默认值。
- `reject` 保留为最严格的程序化安全默认。
- `agy-owned` 保留一个版本用于兼容 0.6.x，但标记 deprecated；它继续忽略 DSH schemas，不能承诺 DSH 原生权限和 MCP 生效。
- `dsh-owned` 强制使用无内部工具的 AGY Agent，避免 DSH 与 AGY 双重执行。

### 4.2 结构化 tool-call envelope

当本轮有 DSH tools 且策略为 `dsh-owned` 时，Provider 不再向 AGY 传 `--json-schema`。它把本轮经过清洗的 DSH tool schemas 编码进 bounded prompt contract，并在本地执行完整 JSON/allowlist/参数校验：

```json
{
  "kind": "tool_call",
  "name": "write_file",
  "arguments": {}
}
```

或：

```json
{
  "kind": "message",
  "content": "普通文本回答"
}
```

具体约束：

- tool name 使用本轮 DSH schemas 的精确 allowlist。
- 每个工具的 `arguments` 使用对应 DSH input schema，不接受未知工具或未验证参数。
- 第一版每次模型响应最多产生一个 tool call；DSH Agent Loop 执行后发起下一轮。并行调用以后续证据决定，不进入 0.7.0 必做范围。
- Provider 为调用生成 DSH `CallId`，输出 `tool-call-delta` 和 `block-end(tool-call)`，并保证 `usage` 位于最终 `finish` 前。
- contract 只在请求内存中生成，不写入 schema 临时文件；不在日志或错误中记录 tool args/result。
- 没有 tools 时继续使用 0.6.0 文本流路径，避免普通聊天回归。

### 4.3 DSH 执行，Provider 不代执行

Provider 只返回 tool call，不直接调用 `ctx.tools.execute()`。DSH Agent Loop 负责：

1. 展示待执行调用。
2. 通过 ToolRuntime 的 pre-execute、guard、sandbox 和 approval pipeline。
3. 执行文件、shell、web 或 MCP 工具。
4. 把 tool result 写入 Session 并发起下一轮 Provider 请求。

这样可以保持 DSH 既有事件、UI、审批、审计和恢复语义，Provider 也不会绕过会话边界。

### 4.4 Session 上下文只读接入

Provider 插件增加对 DSH `sessions`、`sandboxPolicy` 和 `permissionPresets` 的只读接入，用于一致性检查和 doctor v3：

```text
GenerateOptions.sessionId
  → ctx.sessions.get(SessionId)
  → Session.header.cwd
  → ctx.sandboxPolicy.resolve({ session })
  → permissionPresets.current(session.events)
```

这些信息不用于自行执行工具；它们用于验证 DSH 真实上下文、输出脱敏 telemetry，以及在 context 缺失或互相矛盾时 fail closed。路径只报告 `configured/missing/mismatch`，不写入日志或 doctor JSON。

## 5. 成功标准

1. DSH 中选择的项目自动成为文件和 shell 的工作目录，不需要重复配置 `workspaceRoot`。
2. 同一个 Provider 在 `read-only`、`workspace-write`、`danger-full-access` 三种 DSH 模式下得到不同的 DSH 执行结果，Provider 自身不能提权。
3. read-only 下故意生成写调用时，DSH 稳定拒绝且目标文件不变化。
4. workspace-write 下可以创建/修改项目内 fixture，项目外 sibling fixture 保持不变。
5. shell 调用由 DSH bash/pwsh executor 执行并显示 DSH 审批/沙箱结果；Provider 进程不直接执行模型给出的命令。
6. web tool 与本地测试 HTTP fixture 完成一次受控调用；Provider 不持有网络凭据。
7. 本地 fixture MCP server 的工具可通过 DSH MCP client → tool schema → AGY tool call → DSH execution 闭环返回。
8. danger-full-access 只由 DSH 会话选择触发；Provider argv 不包含 `--dangerously-skip-permissions`。
9. 普通无工具文本、多轮 session、purpose route、retry、usage、image negative result 和 0.6.x 配置保持兼容。
10. 公共 CI 全部使用 fake AGY/Mock tools/local fixtures，`quotaUsed=false`，不访问用户项目、AGY 配置、MCP 凭据或公网。

### 必做

- `dsh-owned` tool policy、配置迁移和 bundle 默认值。
- DSH tool schema → AGY structured envelope → DSH tool chunks 的闭环。
- tool-call/tool-result 历史序列化和恢复。
- DSH Session、workspace、permission 上下文的只读解析与一致性检查。
- 文件、PowerShell/bash、web、MCP 的 Mock/local fixture 集成测试。
- doctor v3、telemetry、兼容性矩阵、双语文档和迁移指南。
- Provider verify 运行 Windows/Ubuntu/macOS × Node.js 20/22/24；DSH native capability smoke 运行 Windows/Ubuntu/macOS × Node.js 22/24。DSH `0.1.0-rc.7` 的 `dsh-code-runtime`/`dsh-mcp-client` 使用 Node 22+ API，Node 20 不宣称 DSH 原生能力兼容。

### 条件性交付

- `--json-schema` tool-call 协议必须在真实 AGY 上可靠通过；失败时不得用 prompt 文本正则冒充 tool call。
- 真实 shell/network/MCP 验证只在 DSH sandbox 和本地 disposable fixture 中执行。
- 0.7.0 tag/npm publish 只有在 DSH Web 中三种权限模式与 tool bridge 全部通过后才允许。

### 明确不做

- 不在插件中复制 DSH 的权限 UI、workspace picker、sandbox、approval 或 MCP 配置页。
- 不让 AGY 和 DSH 同时执行同一个工具。
- 不把 AGY 内部 `tool_call` event 直接伪装成 DSH tool call；0.7.0 候选方案使用无工具 AGY Agent、bounded prompt contract 和本地严格校验。
- 不在 Provider 中直接执行 shell、写文件、请求公网或保存 MCP 密钥。
- 不允许 prompt 或模型返回修改 DSH permission preset。
- 不默认启用 `danger-full-access`，不传 `--dangerously-skip-permissions`。
- 不在本版本承诺并行 tool calls、subagent、后台任务、浏览器控制或 image modality。

## 9. 详细实施计划

### V7-M0：契约与范围冻结

1. 固定 DSH rc.7 的 SessionStore、WorkspaceRegistry、SandboxPolicyService、PermissionPresetService、ApprovalService、ToolRuntime 和 StreamChunk 契约。
2. 固定 AGY 1.1.15 的 `--json-schema`、stream-json、tool-free Agent、取消、超时和临时 schema 路径行为。
3. 明确 DSH-owned 与 agy-owned 的所有权边界、兼容期和弃用说明。
4. 冻结额度、安全 fixture、发布和 negative-result 策略。

验收：公开计划、规划文件和源码事实一致；package/registry 不变；真实请求为 0。

### V7-M1：DSH 上下文接入

1. 将 `ctx.sessions`、`ctx.sandboxPolicy`、`ctx.permissionPresets` 以兼容 rc.7 的方式注入 Adapter runtime resolver。
2. 通过 `GenerateOptions.sessionId` 查找 live Session；解析 immutable cwd、effective sandbox mode 和 permission preset。
3. 校验 cwd 为绝对 canonical existing directory，并与 WorkspaceRegistry 记录一致；缺失/失配时对高风险路径 fail closed。
4. 建立 request-scoped immutable capability snapshot，只记录 mode、状态和工具数量，不记录路径、工具参数或内容。
5. 保留无 Session 的 programmatic text-only 路径；任何带工具但无可信 Session 的请求返回稳定错误。

验收：DSH 项目和模式可由 Provider 只读观察；无重复配置；无路径泄漏。

当前实施结果（V7-M1）：

- `src/dsh/context.ts` 已通过 Cordis `ctx.get()` 反射读取可选 DSH service，并将结果收敛为 immutable snapshot。
- 已覆盖 text-only、缺失/未知/非法 Session、workspace mismatch、sandbox/permission/approval 缺失和可信 Session 路径；错误码稳定且不包含路径。
- `toolPolicy: dsh-owned` 已加入配置类型，但在 V7-M2 协议闸门完成前只做上下文校验并安全返回 `UNSUPPORTED_TOOLS`，不会执行工具或 spawn AGY。
- 本地 `verify`、benchmark 和 self-contained DSH Web/headless smoke 已通过；真实 AGY 请求为 0。

### V7-M2：structured tool-call 协议闸门

1. 实现 DSH ToolSchema 到严格 JSON Schema union 的纯函数转换器，限制工具数量、schema 深度、字节数和 unsupported keyword。
2. 实现 message/tool_call envelope、随机 CallId、临时 schema 文件和完整清理。
3. 使用 fake AGY 覆盖 fragmented stream、malformed JSON、未知 tool、参数不匹配、重复终态、abort、timeout 和超限。
4. 在不执行任何真实工具的前提下完成最多 3 次真实 AGY 验证：普通 message、单 tool call、非法/不可用工具不能越过 allowlist。
5. 记录模型/Agent/usage/事件计数和清理结果，不保存 prompt、response、schema、arguments。

验收：真实 AGY 能稳定输出机器可验证 envelope；否则 M2 判定 no-go。

当前实施结果（V7-M2 gate）：

- 已实现纯函数 ToolSchema → 严格 `message | tool_call` envelope schema、allowlist、参数校验、深度/字节/工具数量上限、分片累积和私有临时 schema 文件清理；本地 fake/纯函数测试通过。
- 已为 AGY argv 增加受控 `--json-schema <temporary-file>` 支持；schema 不进入 prompt、日志或错误文本。
- 按冻结预算执行 1 次真实 AGY 协议试验后，`deepseek-proxy` 请求实际产生 `19,031 input tokens`，超过本阶段 `12,000 input tokens` 上限；累计输出 `418`，未继续请求，未保存 prompt/response/schema/arguments。
- 由于请求在预算账本处被安全停止，未取得可接受的 message/tool-call 正面证据；阶段结论为 `NO_GO_RECORD_NEGATIVE_RESULT`，不能进入 V7-M3，也不能把 DSH 工具能力标为可用。
- 随后按剩余全局预算安装并使用真正被 AGY 识别的 `dsh-agy-tool-free`，关闭 slash expansion，并将全局上限调整为 3 次/60,000 input/6,000 output；累计实际为 3 次、`55,682 input`、`580 output`。
- AGY 日志确认 `--json-schema` 已成功注册，slash expansion 已关闭，模型请求最终为 `SUCCESS`；但 `result.response` 为 265 字符、对象样式开头但不是合法 JSON，严格解析返回 `TOOL_PROTOCOL_RESPONSE_INVALID`。因此本次 no-go 已从“预算不足”升级为“当前 AGY 1.1.15 + Agent/structured envelope 路径未可靠产出可解析 JSON”。
- 新增 6 次固定非敏感诊断后已定位具体原因：AGY 1.1.15 在 `--json-schema` 下触发 0th–3th forced invocation，并把多个 planner response 聚合到同一个 final response。结果可能是 4 个 JSON、JSON 与普通文本交错，或多个字段不一致的 JSON；平面 schema、`json`/`stream-json` 和默认/自定义 Agent 均会复现。
- `--json-schema` 结构化请求每次约使用 18k–28k input；无 schema 控制组约 4.4k，并能一次返回唯一合法 tool-call JSON。新增窗口实际为 6 次/`93,037 input`/`861 output`，未执行真实工具。
- 因此 `--json-schema` 路线正式判定 no-go；替代路线为“不传 schema 的 bounded prompt contract + 本地完整 JSON/allowlist/参数 schema 严格校验”，当前仅为 conditional go，不能直接启用 V7-M3。
- 不采用“取第一个 JSON 前缀并忽略后文”、markdown/正则容错或 AGY 内部工具执行；任何前后缀、重复对象、未知工具、参数不匹配或超限均 fail closed。

#### V7-M2b：prompt-contract 可靠性闸门（新增）

## 10. 发布阻断条件

出现以下任一情况不得发布 0.7.0：

- 需要从 prompt、`process.cwd()` 或静态配置猜测 DSH 项目目录。
- prompt-contract final response 不能稳定、唯一地区分 message 与合法 tool call，或任何安全负例未 fail closed。
- Provider 或 AGY 会绕过 DSH ToolRuntime 直接执行桥接工具。
- read-only 能产生文件副作用，或 workspace-write 能无 DSH 审批越过项目边界。
- full access 可以由模型输出、Provider 默认值或 AGY event 提升。
- shell/network/MCP 凭据、参数、结果或 workspace path 进入日志。
- retry、resume 或 abort 可能重复执行有副作用的 tool call。
- 公共 CI 调用真实 AGY、访问公网或读取用户配置。
